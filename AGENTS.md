# namera repository guide

namera is a pnpm workspace written in TypeScript 7 with Effect v4, laid out like the Effect
repository, plus a Foundry project for the Solidity contracts. Read this file before changing
anything, then load the skills under [Skills](#skills) that match the task.

## Workspace map

- `contracts`: `@namera-ai/contracts-sol` (private), the Foundry project with Namera's Smart Sessions,
  session validators and policies. Its own tooling (`forge fmt`, `forge lint`, `forge test`, Slither, Halmos)
  applies there; see `contracts/README.md`.
- `packages/contracts`: `@namera-ai/contracts`, ABIs and deployment addresses of Namera's Smart Sessions contracts.
  `src/` is generated by `pnpm contracts:generate`; never edit it by hand.
- `packages/sdk`: `@namera-ai/sdk`, session keys, policies and grants for agents on Kernel 3.3 smart accounts
  (EntryPoint 0.7, deployed or through EIP-7702), the one account Namera supports. The
  Promise API (`.`) and the Effect API (`./effect`) mirror each other; `src/internal/` holds the one implementation.
  Barrels, the exports maps and `src/internal/version.ts` are generated by `pnpm codegen`.
- `packages/devnet`: `@namera-ai/devnet` (private), the local devnet tests run on: anvil and alto per Vitest worker
  with EntryPoint 0.7, Kernel 3.3 and Namera's contracts, and its controls (`isolate`, `fund`,
  `sendUserOperation`, `bundlerClient`, time). A second chain (31338, `Devnet.from(context, { chain: "second" })`)
  starts only for the multichain tests that connect to it. `src/internal/bytecode.ts` is generated by `pnpm codegen`.
- `packages/*`: publishable packages, each with its own public boundary.
- `apps/*`: runnable applications (private).
- `scripts/`: the repository's tooling, one Effect CLI (`node scripts/bin.ts <command>`): checks, code generation,
  contract deployment and provenance records, release checks, and Namera's oxlint rules (`scripts/oxlint/`).
- `scratchpad/`: ad hoc probes: `scratchpad/<name>.ts`, run with `node`, deleted afterwards (git
  ignores everything there but its skeleton).
- `.changeset/`: pending release notes.

Dependencies point inward: apps depend on packages, packages never depend on apps.

## Commands

| Command                   | What it does                                                                     |
| ------------------------- | -------------------------------------------------------------------------------- |
| `pnpm check`              | Everything CI runs, in order. Run it before every push.                          |
| `pnpm typecheck`          | Type-check everything with tsrs (TypeScript 7 + Effect diagnostics)              |
| `pnpm lint`               | oxlint with Effect's and Namera's rules, then `forge fmt --check` + `forge lint` |
| `pnpm format`             | Format with dprint (`format:check` only checks)                                  |
| `pnpm test`               | Run every Vitest project once (`test:watch` for watch mode)                      |
| `pnpm build`              | `tsc -b`, then each package's build                                              |
| `pnpm circular`           | Fail on import cycles between modules                                            |
| `pnpm test:types`         | Type tests (`packages/*/typetest/*.tst.ts`) with tstyche                         |
| `pnpm test:docs`          | Run the `ts import.meta.vitest` examples in TSDoc                                |
| `pnpm test:contracts`     | The Foundry tests                                                                |
| `pnpm docs:check`         | Check TSDoc against the documentation rules                                      |
| `pnpm codegen`            | Regenerate barrels, exports maps, the SDK's version module and devnet bytecode   |
| `pnpm codegen:check`      | Fail when a generated file (`@namera-ai/contracts` included) is stale            |
| `pnpm check:dist`         | Type-check the built declarations like a consumer                                |
| `pnpm api-snapshot`       | Rewrite `packages/<name>/etc/<name>.api.md`; review the diff, it is the API      |
| `pnpm bundle-size`        | Bundle `bundle/budgets.json` fixtures with rollup and esbuild, fail over budget  |
| `pnpm type-cost`          | Type-check cost of each `typeperf/` consumer against its baseline (`--update`)   |
| `pnpm ox-pin`             | Fail when the SDK's `ox` is not the exact version viem depends on                |
| `pnpm pack:check`         | Pack each package and check it with publint and attw                             |
| `pnpm contracts:<action>` | `status`, `deploy`, `record`, `verify`, `generate`: see `contracts/README.md`    |
| `pnpm changeset`          | Record a change to a published package                                           |

`pnpm typecheck:tsc` runs the official `tsc` and is for CI. Agents use `pnpm typecheck`.

Also: `pnpm coverage` (v8 coverage), `pnpm --filter @namera-ai/sdk mutation` (StrykerJS on `src/internal/core`, 100%
break threshold), and the SDK's runtime smoke test as the CI `Runtime` jobs run it:
`NAMERA_RUNTIME_TESTS=1 pnpm vitest run --project @namera-ai/sdk/runtime` (with Bun or Deno) or
`--project @namera-ai/sdk/browser` (Chromium, which also runs the WebCrypto key store's tests in `test/browser/`). The OS
keychain store's suite runs only with `NAMERA_KEYCHAIN_TESTS=1` (the CI `Keychain (macOS)` job), since it writes to
the machine's real keychain.

## Validation

Use the narrowest validation that covers the change, then `pnpm check` before pushing:

| Change                         | Validation                                                                        |
| ------------------------------ | --------------------------------------------------------------------------------- |
| Source or tests                | `pnpm lint:fix`, `pnpm format`, `pnpm test <file>`, `pnpm typecheck`              |
| Public API                     | Also `pnpm docs:check`, `pnpm codegen` when a module is added or removed, and     |
|                                | `pnpm build && pnpm api-snapshot` (review the report)                             |
| Type-level behaviour           | `pnpm test:types <file>`, `pnpm typecheck`, `pnpm type-cost` after `pnpm build`   |
| TSDoc examples                 | `pnpm test:docs <file>`, `pnpm docs:check`                                        |
| Exports, `package.json`, build | `pnpm build`, `pnpm check:dist`, `pnpm bundle-size`, `pnpm pack:check`            |
| Solidity                       | `pnpm test:contracts`, `pnpm lint`, then `pnpm codegen:check` (ABIs and bytecode) |
| Docs only                      | `pnpm format`                                                                     |

Report every command you could not run.

## Tooling

Configuration lives at the root: `dprint.json`, `.oxlintrc.json`, `tsconfig.base.json` (compiler
options and the Effect language service), `tsconfig.packages.json` and `tsconfig.tests.json`
(project references), `vitest.config.ts`, `lefthook.yml`, `commitlint.config.ts`.

TypeScript is TypeScript 7 (tsgo), patched with the Effect language service by `pnpm install`
(`effect-tsgo patch`), so `pnpm typecheck` reports Effect diagnostics. Fix what they flag; silence
one only when the flagged pattern is the point, for the next line only
(`// @effect-diagnostics-next-line <rule>:off`). oxlint runs Effect's own rules
(`@effect-kit/oxc`): import modules (`effect/Effect`), not barrels; relative imports end in `.ts`;
`Array<T>`, not `T[]`. Namera's rules (`scripts/oxlint/`) keep the SDK's layers apart: only
`src/internal/promise.ts` runs effects (`namera/no-effect-run`), a feature imports only its own or
its ancestors' `internal/` (`namera/no-foreign-internal`), `src/internal/core` is viem-free, and only the viem
adapter `src/internal/viem/` imports viem (types included), so another viem major is another adapter.
Never disable a rule file-wide.

Packages export their source during development (`"./*": "./src/*.ts"`) and their build when
published (`publishConfig.exports` → `dist`), so tests and type checks never need a build. Builds
are `tsc -b` plus Babel's pure-call annotations, so bundlers tree-shake them like Effect. The
publish build (`pnpm release:build`) turns `stripInternal` on and re-checks the declarations.

Install [Foundry](https://getfoundry.sh) 1.9 before `pnpm install`: the contracts package installs
its Soldeer dependencies then, and the devnet runs anvil.

## Repository scripts

Every repository script is a command of the Effect CLI in `scripts/`: `scripts/commands/<name>.ts`,
registered in `scripts/cli.ts` and run as `node scripts/bin.ts <name>` (root `package.json` scripts
call it). No JavaScript under `scripts/`: `pnpm lint` fails on `.js`/`.mjs`/`.cjs` files there.

- Keep commands thin: flags and wiring in the command, logic in exported functions that
  `scripts/test/` tests with real temporary folders (`FileSystem.makeTempDirectoryScoped`).
- Fail with the CLI's errors (`CheckFailed` for problems found, `ToolFailed` for a tool that failed);
  `scripts/bin.ts` reports them and sets the exit code. Run other tools through the `Tools` service.
- Config files (`vitest.config.ts`, `commitlint.config.ts`) are plain TypeScript: their tools load
  them.

## Dependencies

- Root and development dependencies are exact versions; published packages declare ranges
  (`^4.1.5`) for `dependencies` and `peerDependencies`. `effect` is a peer of every library.
- The pnpm catalog holds versions more than one package.json uses.
- The SDK pins `ox` to the exact version its viem depends on (`pnpm ox-pin` checks it), so an app bundles one ox and
  one `@noble/*`; upgrade them together.
- New releases must be a day old before they install (`minimumReleaseAge`), except `effect`,
  `@effect/*` and `@effect-kit/*`. Dependency install scripts are denied unless listed in
  `allowBuilds`.

## Code guidelines

Load the `effect-conventions` skill before writing or reviewing code.

- Name things for what they are in the domain, consistently: one name per concept.
- Use what exists before writing a helper: Effect (`Array`, `String`, `Option`, `Schema`,
  `Predicate`, …), then the workspace's own modules. Never create catch-all `utils` or `helpers`.
- Inline one-off logic; extract only substantial or reused logic into a specifically named module.
- Separate logical blocks with a blank line (setup, validation, execution, result); dprint does not.
- Public functions declare their signatures explicitly, as Effect does
  (`export const make: <A>(a: A) => X<A> = …`).
- Every export of a published package has TSDoc with `@since`, `@category` and `@stability`, and
  examples as `**Example** (Title)` sections with a `ts import.meta.vitest` fence. Preserve existing
  public APIs when cleaning up.
- Comments explain why, not what.

## Tests

Tests live in each package's `test/` folder, mirroring `src/`, import the package by name, and use
`@effect/vitest` (`it.effect`, `assert`), never `vitest` directly. Write the tests a behaviour needs:
the documented contract, its failure cases and regressions; leave what the type checker proves to
`typetest/`. The landmines rules are enforced: no test doubles (use real implementations, test
layers, MSW for the network), no fixed sleeps (`TestClock`, or await a signal), no polling races, no
retries, and test file names (`*.test.ts`, fixtures `*.fixture.ts`, helpers
`*.test-utils.ts`). Every test has 10 s (`testTimeout` in `vitest.config.ts`): chain tests wait on the bundler's
simulation, and a test that needs longer belongs in smaller tests or a hook.

- Internal modules are reached through `tsconfig.tests.json` path aliases (`@namera-ai/sdk/internal/promise`), as in
  Effect, and only when no public function carries the behaviour yet.
- Tests that need a chain are named `*.chain.test.ts` and run in the package's `/chain` Vitest project against
  `@namera-ai/devnet`: `devnet.isolate({ beforeEach, afterEach })` and `describe(name, { concurrent: false }, …)`, so
  tests in a file never share chain state. Everything else is a unit test and runs without a chain
  (`pnpm vitest run --project @namera-ai/sdk`).
- **The devnet's alto runs in safe mode only**: it traces every user operation and rejects what breaks ERC-7562, as
  the shared mempool does, so chain tests never rely on a lenient bundler. Never turn it off, and never route a test
  around a rejection. Fix the operation; when the rejection is what mainnet would do too, keep the devnet's state
  matching mainnet (stakes included, such as Kernel's FactoryStaker) and test the limitation. `patches/@pimlico__alto@0.0.21.patch`
  makes safe mode work on anvil (pimlicolabs/alto#810 and two anvil tracer differences); re-check it on every alto
  upgrade and drop what alto fixes.

## Commits and pull requests

Conventional Commits with kebab-case scopes (`feat(sdk): add retries`); commitlint checks commits
and the `PR title` workflow checks PR titles, because PRs are squash-merged.
Add a changeset for every change a consumer of a published package can observe.

## Learning more about Effect

Before writing Effect code, read `node_modules/effect/AGENTS.md` completely and follow its links
when needed. For anything it does not cover, search `node_modules/effect/src`. Never rely on
Effect v3 knowledge.
